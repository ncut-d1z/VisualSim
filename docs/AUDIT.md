## 1. 审计原则

1. **只改目标仓库**：允许读取来源仓库 ncut-d1z/ros2-vio-node 的资料，但禁止修改它；本轮只允许写入目标仓库 docs 下的审计文件和被审计的四份 Markdown 文档，禁止改生产代码。
2. **先登记、后审计、再整改**：先在 AUDIT.md 写明依据/规则，在 AUDIT_PROGRESS.md 列全对象、全部问题与初始状态；再逐文件对照当前 main 的真实内容扫描。不能把外部审核意见当成源码已证实的事实，也不能因意见说“已冻结”就跳过实查。
3. **按层次审计**：SRS 只描述最终功能、边界和验收，不写代码迁移；HLD 描述架构、模块/数据流/部署；LLD 明确签名、错误、算法、公式、状态边界；IMPLEMENTATION_PLAN 专门写实施阶段、迁移、测试、命令与追踪矩阵。
4. **以冻结 v1 合同为底线**：本轮只修歧义、边界、图文时序、引用、映射、Markdown 及命令可靠性。不改变即时式双类别运动规则、BeginMotionMode/EndMotionEnd 名称、按纳秒历史重算、无计算结果缓存、动态多相机、Room 唯一场景、非 ROS、Ubuntu 24.04、禁止 Windows、禁止重复生成同一传感器时间戳等已冻结条件。
5. **证据化记录**：AUDIT_PROGRESS.md 必须逐文档列出相对路径和审计状态；逐问题列出编号、涉及的相对路径、整改目标、严重性、整改状态、定位与核查结果。不得只写“已整改”而无改动/符合性说明。
6. **审计状态定义**：空白＝尚未扫描；正在审计＝已开始但未闭环；已审计＝当前版本已完成审阅、问题已记录。整改状态：未整改＝存在/尚未核实；已整改＝已更正文档并复核；无需整改＝当前文档原已满足目标并写明证据。已审计不必等于全数已整改；总体关闭仍需所有必须修问题有结论。
7. **发现新问题**：先在 AUDIT_PROGRESS.md 新增文件相对路径及整改目标，再修改对应文档；必要时在 AUDIT.md 补充规则。最终逐项复核和记录实际提交版本；不声称已经编译或运行测试。
8. **差异和冲突处理**：SRS §10 为概览、PLAN §8 为唯一完整追踪矩阵；映射以二者语义一致为准，不能通过删除需求或验收项来消除差异。LLD 的公式/状态合同优先于 HLD 的示意图细节，但如发现实质冲突，应同步更新三者并报告。
